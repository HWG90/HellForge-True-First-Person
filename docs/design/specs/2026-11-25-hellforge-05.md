# HellForge 0.5: the fields it moves (2026-11-25, round 34)

The user upgraded HellForge to 0.5.0-beta (SDK 20). In 0.5, HellForge itself enlarges the world's entity table.
modloader.log puts it this way: "entity table: 4096 records a world (the game's 2048) and entity maps of 8192 slots,
behind the Game block". HellForge moves the 24-byte entity records out of the EntityManager and rewrites every game
instruction that addresses them. True First Person read those records at the game's fixed offset (EntityManager
+0xF32F18). On 0.5 it would not find the local Helldiver, so first person never arms, or it would read the wrong record.

**Nothing here has run in the game.** The branch is round34-hf05. It does not change the version.

## 1. What the SDK says

`app/sdk/docs/modding/hooks.md`, "Fields a mod moved", and `hellforge_globals.h` (EntityManager, PlayerManager):

- The entity records can move. They may lie outside the manager, and before it too, so their offset is signed. The
  records' offset from the manager is 8 times the signed 4 bytes at game.dll+0xFD9DDE (0xF32F18 in the game).
- PlayerManager's count (0x84), peer ids (0x2C8), lifecycles (0x2E0), player descriptors (0xE8) and network ids (0x3A8)
  can move too. That happens when a mod grows a per-player list. Each has a documented instruction site.
- Check the instruction first: code_matches on the bytes before the displacement. Then refuse a value that is not
  aligned or not inside the manager. HellForge checks eight instructions for the records against each other.

The following are not on HellForge's list, or the mod does not read them:

- **AvatarManager.** The SDK says HellForge follows it, but it gives no sites. The mod reads its map at +0xF8, its
  count at +0x6C, its descriptors at +0x110, and its rows of 0x1238 bytes at +0x53E880, +0x53E9B8 and +0x53E9A4. A moved
  avatar list is refused, not misread. Every snapshot compares the avatar descriptor it finds there, byte for byte, with
  the entity record (`snapshot.c` "Avatar descriptor changed"). The steering pin also holds the avatar map's
  displacements.
- **CustomizationManager and ScoreManager.** The mod never reads them.
- **The player capacity byte** (game+0x540870). The mod keeps no per-player arrays. It reads the local player's slot 0
  only.
- **Wielder, weapon pool and inventory.** They are not on the SDK's list.

## 3. What changed

- **`src/entity_fields.h`** (header only, so no build lists change). It reads each movable field from the game's
  code, at fifteen instructions:
  - the records at game+0xFD9DDE (EntityDescriptor, 8 × disp, signed; the SDK's site), cross-checked against
    game+0xFD9C53 (EntityOfNetwork, the record's +8: disp + 1);
  - both map headers from the four reads of each lookup (buckets, capacity +8, empty +12, multiplier +16);
  - the player count at game+0x62C727. The second count is game+0x128D836 and must be count + 4;
  - the descriptors at game+0x62C755;
  - the network ids at game+0xACC670, which must equal game+0x128D83F.

  Each instruction is checked before its displacement is used. The bytes before and after it are read the way
  code_matches reads them (read_code). The displacement itself is read live (HellForge's `read`), because the bytes
  "before any hook" may be the game's original ones. The values must hold together:
  - the records: the two sites agree, nonzero, and not on the manager's own fields (0 < x < 0xF32F18 refuses);
  - each map header: 8-aligned, inside 32 MiB, and its four fields in order;
  - the player fields: aligned, inside 64 KiB, and both counts and both network-id sites agree.

  A failed read waits, because the page may still be cold. A mismatch refuses. `tools/verify_entity_sites.py` checks
  all fifteen against the image: each one holds the game's own offset there, with the bytes the header says.
- **The session reads them once.** `mod_view.c` reads them on the game thread after the code pins pass and before
  `start()`. HellForge rewrote the code when game.dll loaded, before the game built the manager, and it never changes
  in a session. The mod logs one line:
  `Ready: fields read from the game's code: entity records manager-0x… (moved), network-id map +0xf22ec8 (the game's own), …`
  A refusal logs `Refused: the entity and player fields could not be read from the game's code: <site and why>. True
  First Person stays off for this session.` A cold page logs `Waiting: …` once, and the read is tried again with the
  pins.
- **The readers.** The result goes to every reader:
  - `TfpOpsHost.fields` (the backend snapshot and descriptor);
  - `FpMemory.fields` (`snapshot.c`, `backend.c`, `models.c`, `preferences.c`; the motion sampler and the arm drive's
    host);
  - `TfpNativeAimHost.fields` (the native aim option).

  The option, and the donor's preferences, refuse while the player fields are moved, because their +0xD0 / +0x2EC
  rows are not followed. A reader handed nothing uses the game's own offsets in the tests. In the shipped view and feel
  DLLs it refuses: build.sh passes `-DTFP_FIELDS_REQUIRED`. Fields that were handed in unresolved always refuse with
  "Entity fields unresolved".
- **The pose helper** runs in the game's own calls, so it does no new read there. `tfp_pose_set_entity_fields` copies
  the session's values once, before the helper runs. The look-gain steering (`input_steering`, retail's copy of the
  game's EntityOfNetwork) reads the network-id map, the record's +8 and the two player fields from those values.
  B_PIN_9 and B_PIN_STEERING now hash their moved-field displacements as zeros:
  - B_PIN_9: 0x4F44ABD28DFD84FA, five displacements;
  - B_PIN_STEERING: 0xF4122F2D563E703F, two displacements.

  The pin still proves every instruction, and the displacements are left to the check above. Before this change the
  pins went through read_code. Depending on what read_code returns for HellForge's rewrite, they either refused the
  look gain on 0.5 or let it read the game's own place. `tests/diff_pose_helper_open.h` carries retail's masked hash
  (0xA5FF70BD20FB7378). `tools/find_look_gain.py` checks the masked B_PIN_9.
- **The maps of 8192 slots.** The map lookups read the capacity from the header, as the game does, so a grown map is
  followed. The probe bound stays at retail's 4096. A map of 8192 slots holds at most 4096 records, so a probe reaches
  the key, or an empty slot, within 4097 steps. The one case past the bound is a missing key behind 4096 occupied slots.
  That refuses either way, "Entity absent" or "Entity lookup bound reached".

The SDK's own functions (`hf_fn_EntityDescriptor`, `hf->entity_of_network`) are not used, for two reasons. The
snapshot needs the whole 24-byte record (the network id, the authority bit, the descriptor the avatar and weapon lists
are compared with), and it is read from the tick, the primary-draw hook and inside the game's own calls. Reading the
displacement gives the same record with guarded reads and no game call. The manifest still declares SDK 16: nothing
here needs more (`read`, `read_code`), so HellForge 0.4 loads it as before.

## 4. Tests

- `tests/run-entity-fields.sh` (new), built twice: as the tests are, and with the shipped build's rule.
  - The resolver: the game's own code (0.4) gives the game's own offsets. Records moved −32 MiB and +2 GiB are found.
    The live displacement wins over a code reader that still holds the original.
  - Refusals: record sites that disagree, records on the manager's own fields, an unreadable site (waits, naming it),
    a mismatching byte before or after a displacement (refuses, naming it), a map header moved whole (taken) or broken
    (refused), player lists moved by +0x400 (taken) or with one site not rewritten (refused).
  - Both snapshots: with the records in place, and moved before the manager with the game's place cleared. The game's
    offsets then refuse ("Local player generation unavailable"), and the moved ones find the same player and weapon.
    Also with the player fields moved, and with unresolved fields.
  - The network-id map grown to 8192 slots: the key hashes into the upper half, behind 300 ids that wrap past the
    last slot, and its record (3000) lies past the game's 2048.
  - In the shipped build, a reader handed nothing refuses.
- `tests/run-vectors-backend-ops.sh` runs every retail script a second time with the records moved −32 MiB. The fake
  process serves the records there and denies the game's place, and every answer must still be retail's.
- Every existing runner, the harness unit tests and the feel build pass (section 6 of the commit message).

## 5. What only the game can show

- What HellForge 0.5's displacement at game+0xFD9DDE actually holds, and that game+0xFD9C53 was rewritten with it (the
  Ready line says it). If HellForge rewrote one and not the other, the session refuses and names both.
- Whether read_code returns the rewritten or the original bytes for HellForge's own rewrite. The instruction check
  works either way. The displacement is read live.
- That the map headers stayed in place (HellForge says the maps grew to 8192 slots, not that their headers moved). If
  they moved, the Ready line says "moved" and the new place is used, as long as the four reads agree.
- That the local player is found, first person arms, and the look gain's steering works with the moved records.
- The second issue the Bingus harness review noted (far fewer loadout packages loaded on 0.5 before it stopped) is not
  addressed here. It is outside this mod's reads.
