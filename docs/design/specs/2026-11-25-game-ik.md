### What that means

The drawn left arm is posed by the rig's own IK chain `0C92A44D` (shoulder, elbow, hand) onto the gun's own IK_left
whatever the drive writes into nodes 10, 12, 13. It fits everything seen:

- The keep test: the writes reach the rig (the socket moved the camera), the left hand on screen is still the IK's.
- Reload arms show the drive's writes (an IK whose target leaves the hand, or whose weight drops in an action, lets them
  through); nobody reported frozen reload arms.
- The probe's "only recoil 0.002 to 0.006 on fire": the IK following the recoiling gun.
- "The rig's own static hand is at the gun's IK_left" (round 38): it is solved there.

**Not proven:** where the IK runs against the render hook. The drive's own "as drawn" reads node 13 on the grip straight
after its `World.update_unit` (exe+0x336530 → 0x1b2dc0: as far as it was read, the scene graph's evaluation 0x596f80 and the transform messages 0x4f20b0, no animation), so
the IK must be applied after that read and before the frame reaches the screen, or on the renderer's side. The fix below
does not depend on when: it moves what the IK aims at, and keeps it moved through the draw.

## What changed

1. **`src/game_ik.h`** (new, pure): the ease (`tfp_gik_ease`, linear over the slide's time; 0.25 s for every distance until
   the second pass below, now `tfp_gik_seconds` of the distance), the shown share (a
   smoothstep), the node's record at a share (`tfp_gik_pose`: the shorter way round, the position straight, the record's
   other words the game's), the node where the game keeps it (`tfp_gik_unmoved`), the reasons' words.
2. **`src/arm_drive.c` `gik_frame`** (after `grip_frame` in each driven frame): while the hand is held on an attachment's
   grip node (`d.grip.held`, `d.grip.attachment`), the gun's own IK_left (the first node named 67C94E4B on the gun; it
   must be a leaf hanging on another gun node, else refused) gets the attachment node's pose in the frame of the node it
   hangs on, read from the evaluated worlds this frame, through the same guarded setter (UnitAPI+0x60) and
   `World.update_unit` of the gun. Eased in and out in the time the distance asks (second pass below; first 0.25 s for
   all, sized for the AR-23's 0.124 m only). When the held grip node itself changes while the node
   is moved (another grip node of the attachment, or the attachment made again), the aim slides from where it was to the
   new node over the same 0.25 s (`tfp_gik_cross`) instead of jumping there.
   - **Put back exactly** (the game's own record, recovered as `tfp_graft_underlying` does for the rig: a game write in
     between is kept): at once when the gun changes or goes away (a hold's stow), when the drive is not driven (another
     camera, a refusal), on `tfp_arm_drive_release`, and when switched off (`game_ik_off.txt`, or the grip off); eased
     when the hand lets go (the gate: an action, far, fast) or the attachment goes (on the last target read).
   - **Not put back after the draw.** Round 13's put-back is of the rig only; the IK is to find the node moved whenever
     it looks. The node is a locator: no mesh hangs on it, nothing hangs on it (checked).
   - **The gate and the log see the node where the game keeps it** (`grip_node_world`): the body's own IK follows the
     same node (its chain has the same target), so without that the gate would track a hand that moves with the node.
   - **The drive's own reach stays on.** It aims at the same pose (the grip's node), so the IK's input is already its
     answer if the IK runs after it, and the hand is still on the grip if it does not. The fingers' curl
     (`src/grip_fingers.h`) stays on for the same reason: the IK turns the arm, not the fingers. Whether the curl is
     needed is for the game run to show (below).
   - Only the gun the drive proved on the local player's rig socket.
3. **The log**: a line of its own, `Grip: hand: held by the game's IK, its target (the gun's own IK_left) moved onto the

### Blocking: the slide tripped the mod's own gate on far grips

The third-person body's hand follows the same node, and the gate lets go of a hand moving faster than 0.9 m/s against the
gun. A 0.25 s smoothstep peaks at 1.5 x distance / 0.25: 0.99 m/s at 0.165 m. With the body's hand on the node as moved
(`tests/arm_drive_test.c` `test_game_ik_follow`; the fake engine now evaluates the gun on `World.update_unit`), 600
frames of 16 ms:

| 0.080 m | 0 | 585 | 0 | 584 | 0.27 s | 0.45 m/s (was 0.48) |
| 0.126 m | 0 | 585 | 0 | 574 | 0.42 s | 0.45 (0.76) |
| 0.146 m | 0 | 585 | 0 | 570 | 0.49 s | 0.45 (0.87) |

| 0.180 m | 54 | 0 | 0 | 563 | 0.60 s | 0.45 (1.08) |
| 0.220 m | 54 | 0 | 0 | 555 | 0.73 s | 0.45 (1.32) |

Two changes, either of which alone stops it:

- **The slide takes the time its distance asks** (`tfp_gik_seconds`): the smoothstep's peak is held at
  `TFP_GIK_PEAK_MPS` = 0.45 m/s, half the gate's, the time within 0.25 to 0.8 s (0.8 s covers 0.24 m). The slide of a
  changed grip node is timed the same way by its own length.
- **The gate leaves the mod's own move of the node out** (`gik_commanded`, `grip_track`): each sample of the body's hand
  keeps how far this mod had the node from the game's record then, the speed is taken both as read and with that left
  out, and the lesser is the hand's. So a hand that follows the node reads its own motion only, and a hand that does not
  follow (the game may not move the body's hand with the node: not known) reads as before.

The test also runs every distance with a 0.24 m/s sway of the hand (all five phases at 0.126 m, where the check saw one
let-go in five), a 0.6 m/s sway (under the gate by itself, over it with the slide added), and a hand that stays behind,
alone and with the 0.6 m/s sway: no let-go, the node arrives and stays.
