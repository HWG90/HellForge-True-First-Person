# The unzoom gate that flips every frame

Written 2026-11-23, after soak 21 on 0.6.0-feel.46. This build (branch `round8`) changes one thing the player can
see (the kept speed, part 4) and otherwise only logs. The fix for the cause waits for what the two new log lines
show in the game.

## The finding

Standing still with the LAS-5 Scythe in the native view, the first-person rig's eye went about 0.2 m back and forth
along the view's forward axis **every frame**, for 2.3 seconds (soak 21, 03:13:50 to 03:13:53). The player saw the
world shake at 15 Hz and, at the next event, the view thrown 0.435 m past the far place.

The three reports, all under `~/.cache/tfp-altdiag` on the machine that ran the soak:

- `REPORT-B.md`: the cause. The game's own evaluator of camera kind 6 turns the lens towards the wide third-person
  target (90 degrees) while an "unzoom gate" is set, and towards the weapon's own (60 degrees for the Scythe) while
  it is clear. The gate was flipping every frame. The proof is the lens number: a target that flips 60/90 each frame
  settles the lens at exactly 67.6 degrees after a gated frame and 63.8 after a clear one, whatever the frame time,
  and the log shows those two numbers for the whole episode. The rig eye follows the gate.
- `REPORT-A.md`: what the player saw, and why the eye's continuity let it through: it looks for jumps only for
  600 ms after an event, and the flipping went on long after. A guard that holds the eye in the middle was tried
  there (`proto/camera_continuity.h`).
- `REPORT-C.md`: a sceptic's review. The same signature is in 19 of 21 soak logs, back to 0.6.0-feel.37; in soak 19
  it ran for three seconds after a sprint stopped, with no weapon swap at all. It is not a rare race at one entry.

What is **known**: the lens target flips each frame through the game's gated branch; the rig eye moves with it; the
presented camera is not part of the loop (the eye kept flipping while the continuity held the presented eye still).

What is **not known**:

- Which of the two gate inputs flips: the avatar's packed bit 0 (copied from byte +5 of the avatar's main row), or
  the request's byte +0x8f. The reports lean to the avatar bit (65 to 75 in 100).
- Whether the mod is part of the loop. The mod's zoom-depth term (`src/pose_helper.c`, the reason-4 return in
  `depth_delta`) is dropped to nothing on every gated frame and added on every clear one, and its pair shifts the
  rig root along the same forward axis. If its size is near 0.2 m, the mod makes the shake itself and may also be
  what keeps the gate flipping. Until this build nothing of it reached the log.

To find episodes in any mod log:

```
grep -nE "fov_native=1\.(113[5-9]|114[0-2]|180[3-8])|asked for (63\.[89]|67\.6) deg" <modlog>
```

Known episodes: `~/.cache/tfp-soak-19.modlog` 07:03:55 to 07:03:58, `~/.cache/tfp-soak-21.modlog` 03:13:50 to
03:13:53.

## What this build logs

### `Gate:` (src/gate_log.h, counted in src/pose_helper.c, written by src/mod_view.c)

One line in a second in which a gate byte changed or the zoom depth was added in some frames and passed in others,
and once in the first second of each native entry (it then ends "the first second of a native entry"). A calm
second writes nothing. A start line says it is watched: `Ready: unzoom gate watched: ...`.

```
Gate: 30 frames of the rig root, the lens read in 30; avatar bit set in 15, changed 30 times; request+0x8f set in 0, changed 0 times; zoom depth added in 15 (-0.2010 to -0.1995 m), nothing to add in 0, passed in 15 (unzoom gate or request state 15); lens target 60.0 to 90.0 degrees, lens 63.8 to 67.6; request+0x88 = 1.000, +0x8d = 0; main row read in 30: +5 set in 15, changed 30 times, +0x3d set in 30, +0x11ac 0.4375 to 0.5210
```

(That is how a second of the soak 21 episode would read **if** the avatar bit is the one that flips and the mod's
depth is about 0.2 m. The frame count, the lens target and the lens are from that log; the rest is made up.)

How to read it:

- **frames of the rig root**: frames in which the helper wrote the rig's root node, one a game frame while a lease
  runs. **the lens read in**: of those, the frames in which the evaluator's lens locals were read; the gate bytes are
  only counted there.
- **avatar bit set in N, changed M times** and **request+0x8f set in N, changed M times**: the two gate inputs. In
  an episode one of them reads about half the frames set and about as many changes as frames. That one is the gate
  that flips. The other should read 0 changes.
- **zoom depth added in N (least to most m)**: frames in which the mod's depth term shifted the rig (and its root
  the other way), and by how much along the rig's forward axis. **nothing to add**: the term was worked out and came
  to nothing (the widest optic). **passed in N (reason count, ...)**: frames it was not applied, by reason. "unzoom
  gate or request state" is the reason-4 return, the one that follows the gate. Other reasons: full aim, no lens read
  for the frame, values out of range, weapon data not read, previous distance not known, over 1 m, weapon data
  changed, zoom policy, depth_off.txt, no evaluator frame, the evaluator's code is not this build's.
- **lens target a to b degrees, lens c to d**: 60.0 to 90.0 and 63.8 to 67.6 is the fingerprint.
- **request+0x88, +0x8d**: as last read in the second.
- A value that is no number is left out of the least and most; "the lens read was no number" and "+0x11ac no number"
  say that none of the second's values was one.
- **main row read in N: +5 set in .., changed .. times, +0x3d set in .., +0x11ac a to b**: the avatar's main row
  (avatar owner + 0x53d8b0 + index * 0x1238) as it stood when the mod wrote the rig root. Byte +5 is what the game
  copies into the avatar bit; by the review's reading of the code it is `+0x3d && (flag == 0 || scalar > 0)` and the
  scalar is the float stored at +0x11ac. If +5 flips while +0x3d stays set, the float is the margin to look at.
  "main row not readable": the two guarded reads failed. The vec3 at +0x10e4 the review also asked for is left out.
- Ends with **depth_off.txt: the mod's zoom depth is forced to nothing** when the switch is on.

### `depth_off.txt` (the depth switch)

A file of that name beside the DLL, read once at the start, makes the zoom-depth term add nothing on every frame
(reason 11, "depth_off.txt" in the Gate: line). Said at the start:

```
Test: depth_off.txt: the mod's zoom depth is forced to nothing on every frame (neither the rig nor its root is shifted for the optic)
```

With it on, the weapon sits where the game puts it for a zoomed optic, without the mod's correction. That is the
price of the test and is expected.

### `Alternation:` (src/camera_alternation.h, counted in src/camera_helper.c)

The detection rule of the guard that was tried, **acting on nothing**: it only counts. A move is a frame whose
wanted eye is 0.05 m or more from where it was; it is a return when it ends within a quarter of its own length of
the place left by the move before, no more than 70 ms earlier; frames count from the second return in a row until a
move that is no return or 70 ms without a move; never in full aim. One line in a second that has such frames:

```
Alternation: 30 frames of the eye going back and forth (would be held; nothing is done), largest move 0.231 m; jumps were looked for in 0 of them; the fire flag was set in 0 (flag byte 12 bit 0x40, not proven on this build); kind 6
```

(About what the seconds ending 03:13:52.020 and 03:13:53.021 of soak 21 would read. The second before would show
some 5 frames, all of them looked at; the second after some 16, three of them looked at.)

How to read it:

- A line beside a fingerprint hit is the guard seeing the episode. Lines **without** a fingerprint hit nearby are
  what the guard would have flattened for another reason: recoil, an explosion's shake, a stagger. Those are its
  false positives, and their number over a soak says whether a guard keyed on the motion alone is safe.
- **jumps were looked for in N**: in those frames the continuity was already taking the flips up itself.
- **the fire flag**: the controller's flag byte 12 bit 0x40, which the helper already reads. No reader of it is
  proven on this build, so a 0 does not prove the weapon was not firing. No read was added for it.

## What this build changes: the kept speed (src/camera_continuity.h, THE WAY BACK)

Where jumps are not looked for, a frame over the measure set the eye's kept speed to its own step whole. A flip of
0.2 m a frame was kept as 6 to 7 m/s, and the first frame looked at afterwards sent the presented eye on at it:
0.217 m and 0.179 m past the far place at 03:13:53.490, 0.435 m carried. Made up, an event 1.5 s into a flipping not
looked at ended 1.0 to 1.5 m from the middle.

Now a frame not looked at that takes the eye back to within a quarter of the move's length of where it was two
frames ago (the move being over the measure) keeps no speed. On the logged frames the presented eye steps 0.050 m at
most where it stepped 0.217 m, and stays 0.106 m from the middle (half the flip) where it was 0.50 m; made up, 0.105 m
at 8, 16.7, 33.3 and 50 ms a frame. A sprint, a dive and a single step keep their speed as before.

This does **not** stop the shake while nothing is looked for: the eye still follows the rig there. It only removes the
throw at the next event.

## What it costs

Nothing new runs in the tick but two takes once a second (a lock, a copy of some 200 bytes, and the line when one is
written), so the `Cost:` line's tick should read as before. In the game's own calls, per frame: the count at the rig
root write and its two guarded reads of the main row (the `Reads:` line gives 0.09 microseconds a read), the
alternation rule at the camera write (two distances), and two vector lengths more in the continuity.

## Experiments to run in the game

Each one: do it, then grep the mod log for the fingerprint and read the `Gate:` and `Alternation:` lines beside the
hits.

1. **An ordinary soak.** No special steps: the review found it several times a session. This alone names the gate.
2. **The provocation.** Scythe out, standing, the view 10 to 30 degrees down. Then either
   - sprint and stop dead, and stand for five seconds; or
   - press 3, turn the view about 60 degrees, press 1, and stand for five seconds.
   Repeat a few times at different places.
3. **The same with `depth_off.txt`** beside the DLL (restart the game with the file there; the log says
   `Test: depth_off.txt` at the start). Same provocation, same number of tries.
4. By eye only, as a cross-check: the same standing still with first person switched off but aiming.

## What each outcome means, and the fix order

**From the Gate: line in an episode (experiments 1 and 2):**

- *avatar bit set in about half the frames, changed about every frame*: the avatar bit is the gate. Read the main
  row: if +5 flips with it and +0x3d stays set, the game's spatial test at +0x11ac sits on its margin.
- *request+0x8f the same*: the reload-ability byte is the gate; the main row does not matter.
- *both steady while the lens still reads 63.8 to 67.6*: the reports' account is wrong; stop and look again.
- *zoom depth added in about half the frames, passed (unzoom gate or request state) in the other half, with a size
  near 0.2 m*: the mod makes the eye's shake itself, whatever flips the gate. Fix A below is due on its own account.
- *nothing to add, or a size of a few millimetres*: the 0.2 m is the game's own depth blend; fix A will not help the
  eye.

**From the same with depth_off.txt (experiment 3):**

- *no fingerprint hits any more*: the mod's root shift closes the loop. Fix A should end the flipping itself.
- *hits remain, with standing `eye_jump` above 0.3 in the View: line*: the loop is the game's own, and what is left
  is the game's share of the shake. It can then only be hidden (fix C).
- *hits remain but the eye's steps are small*: the gate flips by itself but the shake was the mod's: fix A is enough
  for the eye; the lens still breathes 63.8/67.6, which the field-of-view lock already hides.

**The order:**

1. This build: the two lines, the switch, the kept speed.
2. **Fix A**, if the depth is non-zero and follows the gate: at the reason-4 return in `depth_delta`
   (`src/pose_helper.c`), do not drop the term on a gated frame; scale the last supported correction by where the
   lens is between the zoomed and the wide target. The lens cannot jump (2 rad/s at most), so the mod's share of a
   flip falls to about an eighth, and a reload or a dive is eased instead of stepped. The root's pair follows by
   itself. Then soak again with the grep.
3. **Fix C**, if the fingerprint persists with the depth steady or off: a guard keyed on the gate, not on the
   motion: act only while the logged gate byte has changed within the last two frames, hold the eye to the gate-clear
   place, and hold the rig and root pair to the same so the gun does not take the shake over. It cannot flatten recoil.
4. The guard keyed on the motion alone (what `Alternation:` counts): only if its lines over a soak show no false
   positives, and not as the only measure.

## What is not covered

- The Gate: line's counting and the depth switch are tested against the pose helper on the test world
  (`tests/run-wire-pose.sh`) and by themselves (`tests/run-gate-log.sh`); the main row's offsets are from the research
  notes and have not been read in the game yet. If the line says "main row not readable", or +5 never matches the
  avatar bit, the offsets are wrong for this build and the row's numbers must not be used.
- The main row is read when the mod writes the rig root, the gate bytes when the evaluator reads the rig eye, a
  little earlier in the same frame. Whether the game writes the row before or after that point in a frame is not
  known, so +5 can read one frame ahead of or behind the avatar bit.
- A single back-and-forth not looked at, followed at once by an event, still meets the filter with the first flip's
  speed kept: the first move of a flipping is not a return yet.
